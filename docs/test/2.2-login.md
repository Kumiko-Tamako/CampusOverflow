## 一、功能概述

登录签发 JWT 双令牌（Access 15min / Refresh 7d 存 Redis 可吊销），Refresh 采用**轮换**策略（GETDEL 原子消耗防并发重放）；认证依赖 `get_current_user` + `require_roles` 全局可用；`GET /auth/me` 作为受保护示例接口验证链路。

接口：
- `POST /api/v1/auth/login`（200 / 401 / 422）
- `POST /api/v1/auth/refresh`（200 / 401，轮换）
- `POST /api/v1/auth/logout`（204 幂等）
- `GET /api/v1/auth/me`（受保护，200 / 401）

### 5.2.1 修复记录（2026-09-10）

**发现的 bug**：`JwtTokenService.verify_access / decode_refresh` 对 `UUID(sub)` / `UUID(jti)` 无异常保护。攻击者用有效签名密钥签发含**非 UUID 格式 sub/jti**的令牌（如 `sub="admin"`）时，`UUID("admin")` 抛 `ValueError` → 未捕获 → **500 + 栈泄露**，而非 401。

- **修复**：`token_service.py` 两处加 `try/except ValueError → return None`（签名合法但 claims 畸形按无效处理，绝不 500）
- **验证**：L-17（access 路径 sub 非 UUID）、L-18（refresh 路径 jti 非 UUID）新增用例复测通过，均为 401
- **这是上轮独立复测的盲区**：原 L-09 只测 alg:none（在签名校验层被拒，走不到 UUID 解析），未覆盖"签名合法+claims 畸形"这个更深层伪造面

### 5.3 观察项（记录留档，非阻塞）

1. **G（台账约定）**：logout 只吊销 Refresh，**已泄露的 Access 令牌仍有效至 15min 自然过期**——JWT 无状态设计的已知边界。课程场景可接受；如需即时失效，阶段 4 评估 token 黑名单/短 TTL。
2. **防枚举时间侧信道**：用户不存在与密码错误响应信息一致，但 bcrypt 仅在密码验证路径执行，理论上存在微小时耗差异——严格防枚举需 dummy hash，课程项目不做，留档。
3. **Access 同秒签发内容相同**：同用户同秒内签发的 Access 令牌完全一致（iat/exp 相同）——非缺陷，Refresh 轮换靠 jti 保证，Access 靠短 TTL。

### 8.1 发现的缺陷（真 bug，已修复）

**伪造合法签名令牌可触发 500**（F-01/F-02/F-03/F-06，同一根因）：

- **根因**：`token_service.py` 的 `verify_access` / `decode_refresh` 中 `UUID(sub)` / `UUID(jti)` 位于 `jwt.decode` 的 try 块之外——`isinstance(sub, str)` 只挡非字符串、不挡格式非法字符串。签名合法但 sub/jti 非 UUID 的令牌（`UUID("attacker")`）抛 `ValueError` → 未捕获 → **500**。
- **为什么能构造**：`jwt_secret` 默认值 `dev-secret-change-me-in-production` 在仓库中，可离线伪造合法 HS256 签名令牌；`algorithms=["HS256"]` 钉死防的是 alg:none，挡不住"签名合法但 claims 畸形"。
- **影响面**：`/refresh`、`/logout`、`/me` 三端点；无栈泄露（X-02 及格）、服务不崩，但违反"畸形输入必须 4xx"口径；生产覆盖 secret 后外部无法伪造，但缺陷仍在（纵深防御）。
- **修复**（[token_service.py](file:///d:/a_work/CampusOverflow/app/contexts/identity/infrastructure/token_service.py#L37)）：`UUID(...)` 包 `try/except ValueError → return None`（落到既有 401 路径）。
- **回归测试**：`test_jwt_security.py` 补 2 条（伪造 sub="attacker" 的 access/refresh → 返回 None）。
